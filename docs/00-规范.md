# 2048 项目建模规范（唯一口径）

本文件是全部实验文档、图、报告的**唯一真相源**。任何文档里出现的功能名、用例名、类名、图文件名，都必须与本文件一致；本文件未定义的内容一律不得编造。

## 1. 项目定义

2048 是一款单机滑块合并益智游戏。棋盘为 4×4 共 16 格，玩家用方向键（上/下/左/右）使全部方块向该方向滑动，相同数值的相邻方块在滑动方向上合并为一个双倍数值的方块，同一次移动中每个方块最多只参与一次合并；每次有效移动后系统在随机空位生成一个 2 或 4，并按合并所得数值累加本局得分。棋盘出现 2048 时本局胜利；棋盘填满且任意方向都无法移动时本局失败。

约束：本项目为纯单机游戏，无网络、无账号、无多端同步、无付费。

## 2. 参与者

**玩家（Player）**，唯一参与者。

- 无账号体系，不涉及注册、登录、密码、权限。
- 系统内部行为（随机生成方块、判定胜负、累计分数）**不是**参与者。
- 报告中如涉及参与者说明，须写明“本系统参与者唯一”。

## 3. 功能表（F01~F06）

| 编号 | 功能名称 | 操作者 | 功能简述 |
|---|---|---|---|
| F01 | 开始新游戏 | 玩家 | 玩家启动一局新的对局，系统清空棋盘并在随机空位生成两个初始方块（2 或 4） |
| F02 | 移动与合并方块 | 玩家 | 玩家按上/下/左/右方向键，系统将全部方块向该方向滑动，相邻同值方块合并为一个双倍数值方块，同一方块每步只合并一次 |
| F03 | 计分与最高分 | 玩家 | 系统在每次合并后按合并所得数值累加本局得分，本局得分超过历史最高分时更新最高分记录 |
| F04 | 判定胜利 | 系统 | 棋盘出现数值 2048 的方块时，系统判定本局胜利并提示玩家 |
| F05 | 判定游戏结束 | 系统 | 一次有效移动后棋盘已满且任意方向都无法再移动时，系统判定本局失败并提示玩家 |
| F06 | 重新开始 | 玩家 | 对局结束后玩家可清空棋盘并开始新的一局 |

## 4. 用例（UC01~UC06）与关系

| 用例编号 | 用例名称 | 对应功能 | 参与者 |
|---|---|---|---|
| UC01 | 开始新游戏 | F01 | 玩家 |
| UC02 | 移动与合并方块 | F02 | 玩家 |
| UC03 | 计分与显示得分 | F03 | 系统（由 UC02 触发） |
| UC04 | 判定胜利 | F04 | 系统（由 UC02 触发） |
| UC05 | 判定游戏结束 | F05 | 系统（由 UC02 触发） |
| UC06 | 重新开始 | F06 | 玩家 |

用例图必须体现下列关系（`uc-01`）：

- **关联**：玩家 — UC01、玩家 — UC02、玩家 — UC06
- **包含 `«include»`**：UC02 → UC03（每次有效移动后必计分）；UC02 → UC05（每次有效移动后必判定是否还有可行移动）；UC06 → UC01（重新开始即执行一次开始新游戏）
- **扩展 `«extend»`**：UC04 → UC02，扩展点为“棋盘出现数值 2048 的方块”
- **泛化**：本项目无泛化关系。报告中须写一句：“本系统参与者唯一、用例之间不存在父子关系，故未使用泛化关系。”

## 5. 类清单（4 个）

| 类名（英文） | 中文名 | 属性 | 操作 |
|---|---|---|---|
| `Game` | 对局 | `得分: int`、`最高分: int`、`状态: GameState`、`步数: int` | `开始新局()`、`移动(方向: Direction): bool`、`判定胜利(): bool`、`判定结束(): bool`、`结算()` |
| `Board` | 棋盘 | `格子: Tile[4][4]`、`空格数: int` | `滑动(方向: Direction): bool`、`合并()`、`可移动(): bool`、`随机生成(): Tile` |
| `Tile` | 方块 | `数值: int`、`行: int`、`列: int`、`是否新生成: bool` | `升级()`、`清空()` |
| `Record` | 记录 | `最高分: int`、`最近得分: Score[]`、`时间戳: Date` | `读取最高分(): int`、`更新(分数: int)`、`追加(分数: int)` |

类间关系（`cd-01`）：

- `Game` **组合** `Board`（1 : 1，对局销毁则棋盘销毁）
- `Board` **聚合** `Tile`（1 : 0..16，方块可独立于棋盘存在）
- `Game` **关联** `Record`（1 : 1，读写最高分）
- `Game` **依赖** `GameState`（枚举：未开始/进行中/胜利/失败/已结束）

## 7. 写作规范

1. 中文书写，语气客观，不使用“我们认为”“大概”“可能”等模糊表述（第五段反思除外）。
2. 表格用 Markdown 表格；图中文字用中文，类名与操作名用英文（与第 5 节一致）。
3. 引用图统一写成：

   ````
   ```mermaid
   <图源码>
   ```

   图 N 图题
   ````

   - 图以代码块内联，**不使用图片文件**，不写 `![](...png)`。
   - 图号在每份报告内从 1 开始连续编号；同一张图在不同报告中可以有不同的图号。
   - 交付时若需 StarUML 版，把代码块贴入 StarUML 7 的 Tools ▸ Generate Diagram by Mermaid，排版后截图替换代码块；`uc-01`、`bc-01` 需手绘。
4. 报告正文中每提到一张图，必须写出“如图 N 所示”，且图号必须真实存在。
5. 严禁：编造功能、编造参与者、写代码、写算法实现细节、讨论性能与部署。

## 9. 既定取舍（必须在相关报告中如实说明）

1. 无泛化关系（见第 4 节）。
2. 活动图不使用泳道：参与者唯一，无需体现不同实施者。
3. 时序图的激活期由工具生成，覆盖整条生命线，报告只描述消息顺序，不强调激活期粒度。
4. 版本管理实验用 Git 完成，并以对照表说明其与 SVN 的对应关系；条文原文为“练习使用一种版本控制软件实现版本管理”。
