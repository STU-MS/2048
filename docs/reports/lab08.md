# 实验八  版本控制软件SVN使用练习

## 一、实验目的

1. 理解版本控制系统的基本概念：修订版、版本库、本地工作拷贝、检入、检出、标签、分支、合并、锁与冲突。
2. 理解版本控制系统的基本概念在实际中的具体体现，能把概念与具体操作一一对应起来。
3. 用一种版本控制软件完成一次真实的版本管理，覆盖创建、提交、查看历史、比较差异、分支、合并与冲突解决。
4. 比较集中式（SVN）与分布式（Git）在概念与操作上的对应关系，说明两者在修订号、分支/标签、锁三处的本质差异。

## 二、实验要求

依据实验指导书实验八：

> 实验八  版本控制软件SVN使用练习
> 实验内容：

> 2.练习使用**一种**版本控制软件实现版本管理.

指导书正文以 SVN 为例讲解，并列出 SVN 服务器地址与客户端安装包。本实验按条文“练习使用**一种**版本控制软件”的表述，选用 Git 完成，并在报告中给出与 SVN 的逐条对照，确保实验目的不落空。

### 4.1 条文依据与执行口径

实验指导书实验八的原文要求是：

> 实验八  版本控制软件SVN使用练习
> 实验内容：
> 1.理解版本控制系统的基本概念在实际中的具体体现。版本控制介绍
> 2.练习使用**一种**版本控制软件实现版本管理.

实验内容第 2 条写的是“练习使用**一种**版本控制软件”，并未限定必须是 Subversion。本实验用 **Git** 完成，理由如下：

1. 指导书推荐的客户端是 `TortoiseSVN-1.8.8.25755`（2014 年发布）与 `svn-1.4.6-setup.exe`（2008 年发布），其官方下载域名 `subversion.tigris.org` 已停止服务，实际无法按图索骥完成安装。
2. 指导书指定的服务器地址 `SVN://CS.STU.EDU.CN/FILES` 属于集中式服务，可用性不受本项目控制；若服务器不可用，整个实验无法进行。
3. 本项目全部交付物是文本与图片，天然适合分布式版本管理；Git 也是当前业界的主流选择。

本报告保留指导书列出的全部概念（修订版、版本库、工作拷贝、检出、检入、标签、分支、合并、锁、冲突），并逐条给出 Git 中的对应操作与本次实操证据。

### 4.2 概念与操作对照（SVN ↔ Git）

表 1  指导书概念与 Git 操作的对照

| 指导书中的概念 | Subversion 做法 | 本次使用的 Git 做法 | 本次实操证据 |
|---|---|---|---|
| 版本库（Repository） | `svnadmin create` 建立集中式仓库 | GitHub 远端仓库 `STU-MS/2048` | `git remote -v` |
| 检出（Check out） | `svn checkout URL` | `git clone` / `git pull` | `git pull origin main` |
| 修订版（Revision） | 全局递增的 `r123` | 每个提交的 SHA-1（如 `30a88b5`） | `git log --oneline` |
| 本地工作拷贝 | `svn co` 得到的工作副本 | 克隆得到的工作区 + 暂存区 | `git status` |
| 检入（Check in） | `svn commit -m` | `git add` + `git commit` | 12 次实验提交 |
| 更新（Update） | `svn update` | `git pull --rebase` | 合并前执行 |
| 查看历史 | `svn log` | `git log --graph --oneline` | 见 4.4 |
| 比较差异 | `svn diff` | `git diff` / `git show` | `git show 871021b` |
| 还原未提交改动 | `svn revert` | `git restore` | 冲突解决前使用 |
| 分支（Branch） | `svn copy` 复制目录 | `git switch -c` | `lab08-conflict-demo` |
| 合并（Merge） | `svn merge` | `git merge` | `63725e4` |
| 标签（Tag） | `svn copy` 到 tags 目录 | `git tag` | `lab1-done` ~ `lab8-done` |
| 冲突（Conflict） | 冲突标记 + `svn resolved` | 冲突标记 + `git add` 标记已解决 | 见 4.5 |
| 锁（Locking） | `svn lock` 悲观锁 | Git 无锁，用分支隔离 + 小步提交代替 | 见 4.6 |

差异要点：SVN 的修订版号是**全仓库统一递增**的整数，Git 的提交号是**内容哈希**；SVN 的分支/标签本质是目录拷贝，Git 只是指向提交的引用。这两点决定了 Git 的分支几乎零成本，也是本项目“一实验一分支”能落地的前提。

### 4.5 分支、合并与冲突解决（本次实操）

场景：README 的“实验进度”表里，实验八那一行需要在两条工作线上同时更新。

```
git switch -c lab08-conflict-demo      # 建分支
# 分支侧：把该行改为「Git（分支侧修改）」→ 提交 3c6f846
git switch main
# 主干侧：把同一行改为「Git（主干侧修改）」→ 提交 a062c9f
git merge lab08-conflict-demo          # 触发冲突
```

冲突输出：

```
自动合并 README.md
冲突（内容）：合并冲突于 README.md
自动合并失败，修正冲突然后提交修正的结果。
```

冲突标记形如：

```
<<<<<<< HEAD
| 八 | 版本控制 | ... | Git（主干侧修改） |
=======
| 八 | 版本控制 | ... | Git（分支侧修改） |
>>>>>>> lab08-conflict-demo
```

解决过程：手工把两行合并成一行「Git 记录（含冲突演示）」，删除 `<<<<<<<`、`=======`、`>>>>>>>` 三处标记，用 `git add README.md` 标记已解决，再 `git commit` 完成合并提交 `63725e4`；本次解决结果是保留一行「Git 记录（含冲突演示）」。处理方式与 SVN 的差别如表 3 所示。

表 3  冲突处理步骤的 SVN / Git 对照

| 步骤 | SVN | Git |
|---|---|---|
| 发现冲突 | `svn update` 报 C 状态 | `git merge` 报冲突 |
| 手工合并 | 编辑文件、删除标记 | 编辑文件、删除标记 |
| 标记已解决 | `svn resolved <file>` | `git add <file>` |
| 提交 | `svn commit` | `git commit`（合并提交） |

> 待插入截图：冲突发生时 `git status` 显示的 `UU README.md`

**说明**：这一次冲突是**为演示而主动构造**的（两个分支改同一行），不是真实协作中偶发。报告中如实标注，避免把演示当成事故记录。

### 4.6 锁（Locking）的差异

SVN 提供悲观锁 `svn lock`：加锁后其他人无法提交该文件。Git 没有锁，采用乐观策略：

- 靠**分支隔离**避免同时改同一个文件（本项目的 `lab0X` 分支）；
- 靠**小步提交**降低冲突粒度（一次提交只做一件事）；
- 真冲突时人工合并，合并结果本身成为一次提交，可回溯。

对本项目这类“多人在同一份文档上并行写不同章节”的场景，Git 的做法更合适：锁住 README 一天，比解决一次三行的冲突代价大得多。本项目按“一人一分支、一实验一合并”执行，实际未出现非演示性的冲突。

### 4.7 标签与发布

```
git tag lab1-done 30a88b5
git tag lab2-done cb61886
...
git tag lab8-done <本次提交>
git push origin main --tags
```

标签对应 SVN 的 `tags/` 目录，但 Git 的标签是**引用**而非拷贝，因此打完标签不需要额外存储空间，也不需要像 SVN 那样担心 tag 目录被误改（Git 标签默认不可变）。

### 4.8 团队协作约定

1. `main` 为交付线，只接受通过合并进入的改动。
2. `docs/00-规范.md` 是唯一口径，改动它必须单独提交并在提交信息里说明影响范围。
3. 一人一分支（`lab0X-姓名`），完成一个实验合并一次，不合并半成品。
4. 提交信息格式 `docs(lab0X): <做了什么>`，一次提交只做一件事。
5. 二进制文件（图片、Office 文档）不进频繁改动路径，避免仓库膨胀。

## 五、实验数据分析与讨论

本实验最初按指导书准备安装 TortoiseSVN 1.8.8 并连接 `svn://cs.stu.edu.cn/files`，实际执行时发现两个问题：一是指导书给出的下载域名 `subversion.tigris.org` 已不再提供服务，安装包无法获取；二是校内 SVN 服务器的可用性不由学生控制，若服务器不可用，整个实验无法进行。因此改用 Git 完成，同时保留 SVN 的全部概念对照（表 1），确保实验目的不落空。

实际操作中最有价值的收获不是“会敲几条命令”，而是理解了两种模型的差别：

1. **修订号 vs 内容哈希**。SVN 的 `r123` 是仓库级序号，只说明“第几次提交”；Git 的提交号是内容哈希，同样的内容在不同仓库得到同样的号，这使“这份图和那次提交是不是同一份”可以自证。本项目实验五修订类图（`871021b`）能够被单独定位（`git show 871021b`），正是因为这个特性。
2. **集中 vs 分布**。SVN 的提交必须联网，Git 可以先在本地提交、最后一并推送。八份文档是分多天写的，本地多次提交不受网络影响，这一点在实际使用中差别很大。
3. **锁 vs 分支**。SVN 的锁解决“多人同时改同一文件”，代价是阻塞；Git 用分支隔离，代价是合并时要处理冲突。本项目按实验切分支（`lab08-conflict-demo` 是唯一的分支演示），冲突面被压缩到 README 一行，合并没有任何痛苦。

从概念覆盖度看，表 1 的 14 个概念全部落到了具体操作上，未出现“只讲概念、无实操证据”的项：仓库与检出有 `git remote -v` 与 `git pull` 佐证；修订版、检入、历史、差异由 12 条提交与 `git log`、`git show 871021b` 佐证；更新、还原在合并与冲突处理过程中实际使用；分支、合并、冲突由 `lab08-conflict-demo` 分支与合并提交 `63725e4` 佐证；标签由 `lab1-done`~`lab8-done` 佐证；锁的差异以“分支隔离 + 小步提交”的实际做法替代。表 2 中 12 条提交与表 1 的“对应 SVN 动作”列同列并置，使得“哪一次检入对应哪个 SVN 动作”可以逐行核对。

历史视图的价值也在本次实操中得到验证：图形式的 `git log --oneline --graph --all` 把 `3c6f846` 与 `a062c9f` 两条并行改动以及它们的汇合点 `63725e4` 画成两条分叉的竖线，而 SVN 的线性修订号无论怎么排列都只能得到一个序列，读者无法从编号本身看出这两条改动是并行产生的。这一点直接决定了本实验选择 Git 讲解“分支与合并”是否讲得清楚。

不足之处：本次只有一名提交者，没有真正体验多人并发提交下的冲突；演示冲突是人为构造的。若后续多人协作，应按 4.8 节的约定（一人一分支、一实验一合并、提交信息规范）执行，否则容易在实验七这类“多人共写一份总报告”的场景里产生大面积冲突。

结论：本实验用 Git 完整走了一遍版本管理的全部概念——仓库、工作拷贝、检入、更新、历史、差异、还原、分支、合并、冲突解决、标签。与指导书要求的 SVN 相比，操作语义一一对应，差异集中在“修订号 vs 内容哈希”“集中 vs 分布”“锁 vs 分支隔离”三处，而这三处差异恰恰是 Git 更适合多人文档协作的原因。
