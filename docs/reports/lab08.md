# 实验八  版本控制软件使用练习

## 一、实验目的

1. 理解版本控制系统的基本概念：修订版、版本库、本地工作拷贝、检入、检出、标签、分支、合并、锁与冲突。
2. 用一种版本控制软件完成一次真实的版本管理，覆盖创建、提交、查看历史、比较差异、分支、合并与冲突解决。
3. 比较集中式（SVN）与分布式（Git）在概念与操作上的对应关系。

## 二、实验要求

依据实验指导书实验八：

> 实验内容：
> 1.理解版本控制系统的基本概念在实际中的具体体现。版本控制介绍
> 2.练习使用一种版本控制软件实现版本管理.

指导书正文以 SVN 为例讲解，并列出 SVN 服务器地址与客户端安装包。本实验按条文“一种版本控制软件”的表述，选用 Git 完成，并在报告中给出与 SVN 的逐条对照。

### 4.4 冲突与解决

两条线同时修改 README 中“实验进度”表的同一行，合并时产生冲突：

```
自动合并 README.md
冲突（内容）：合并冲突于 README.md
自动合并失败，修正冲突然后提交修正的结果。
```

```
<<<<<<< HEAD
| 八 | 版本控制 | ... | Git（主干侧修改） |
=======
| 八 | 版本控制 | ... | Git（分支侧修改） |
>>>>>>> lab08-conflict-demo
```

解决：手工合并成一行「Git 记录（含冲突演示）」，删除标记，`git add README.md` 后 `git commit`，得到合并提交 `63725e4`。SVN 中对应的是编辑冲突文件 + `svn resolved` + `svn commit`。

> 待插入截图：冲突发生时 `git status` 显示的 `UU README.md`

说明：本次冲突为演示目的主动构造（两分支修改同一行），报告中如实标注。

### 4.5 锁的差异

SVN 支持 `svn lock` 悲观锁；Git 无锁，以分支隔离 + 小步提交替代。本项目按“一人一分支、一实验一合并”执行，实际未出现非演示性的冲突。

### 4.6 标签

```
git tag lab1-done 30a88b5
git tag lab2-done cb61886
...
git push origin main --tags
```

对应 SVN 的 `tags/` 目录，但 Git 标签是引用而非目录拷贝，不占额外空间。

## 五、实验数据分析与讨论

本实验最初按指导书准备安装 TortoiseSVN 1.8.8 并连接 `svn://cs.stu.edu.cn/files`，实际执行时发现两个问题：一是指导书给出的下载域名 `subversion.tigris.org` 已不再提供服务，安装包无法获取；二是校内 SVN 服务器的可用性不由学生控制，若服务器不可用，整个实验无法进行。因此改用 Git 完成，同时保留 SVN 的全部概念对照，确保实验目的不落空。

实际操作中最有价值的收获不是“会敲几条命令”，而是理解了两种模型的差别：

1. **修订号 vs 内容哈希**。SVN 的 `r123` 是仓库级序号，只说明“第几次提交”；Git 的提交号是内容哈希，同样的内容在不同仓库得到同样的号，这使“这份图和那次提交是不是同一份”可以自证。本项目实验五修订类图（`871021b`）能够被单独定位，正是因为这个特性。
2. **集中 vs 分布**。SVN 的提交必须联网，Git 可以先在本地提交、最后一并推送。八份文档是分多天写的，本地多次提交不受网络影响，这一点在实际使用中差别很大。
3. **锁 vs 分支**。SVN 的锁解决“多人同时改同一文件”，代价是阻塞；Git 用分支隔离，代价是合并时要处理冲突。本项目按实验切分支（`lab08-conflict-demo` 是唯一的分支演示），冲突面被压缩到 README 一行，合并没有任何痛苦。

不足之处：本次只有一名提交者，没有真正体验多人并发提交下的冲突；演示冲突是人为构造的。若后续多人协作，应按 `docs/08-版本控制实验.md` 第 8 节的约定（一人一分支、一实验一合并、提交信息规范）执行，否则容易在实验七这类“多人共写一份总报告”的场景里产生大面积冲突。
