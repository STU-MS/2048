# 实验二  UML用例图及用例叙述

## 一、实验目的

1. 理解 UML 用例及用例图，理解参与者的概念。
2. 练习使用 StarUML 绘制出项目的系统 UML 用例图。
3. 理解用例图之间的各种关系（包括关联关系、包含关系、扩展关系以及泛化关系），并在图中标示出来。
4. 编写系统用例叙述。

## 二、实验要求

1. 按“识别参与者、识别用例、确定参与者与用例之间的关系”三个步骤构建 2048 项目的系统用例图。
2. 使用 StarUML 7 绘制参与者、用例，并建立它们之间的关联、包含、扩展、泛化关系（本项目无泛化关系，须在报告中说明原因）。
3. 根据系统业务流程和系统用例简述写出项目的用例叙述，用例叙述按模板的 12 栏填写，基本流程逐步编号，例外流程写出具体分支。
4. 提交实验报告。

## 三、主要实验工具

StarUML 7。

## 四、实验内容及实验数据记录

### 4.1 参与者识别

按实验指导书的判据（参与者位于系统之外；只有使用系统、与系统交互、与系统交换信息的才是参与者；参与者会启动、参与用例）识别，本系统参与者唯一：

| 参与者 | 英文名 | 参与的用例 | 说明 |
|---|---|---|---|
| 玩家 | Player | UC01、UC02、UC06 | 唯一参与者，通过方向键与“开始新游戏”“重新开始”操作与系统交互 |

无账号体系，不涉及注册、登录、密码、权限，故不设“注册用户”“管理员”等第二参与者。系统内部的随机生成方块、判定胜负、累计分数属于系统边界之内的行为，不作为参与者，因此 UC03、UC04、UC05 的操作者记为“系统（由 UC02 触发）”。

### 4.5 用例叙述摘要

六份完整用例叙述见 `docs/02-用例与用例叙述.md` 第 4 节（每份 12 栏）。此处给出 UC01、UC02 两份完整叙述，其余四份列要点。

#### 4.5.1 UC01 开始新游戏（完整叙述）

| 栏目 | 内容 |
|---|---|
| 用例名称 | 开始新游戏 |
| 用例标识符 | UC01 |
| 参与者 | 玩家 |
| 用例简述 | 玩家启动一局新的对局，系统清空棋盘并在随机空位生成两个初始方块（2 或 4） |
| 前置条件 | 系统已启动；当前没有进行中的对局，对局状态为“未开始”或“已结束” |
| 后置条件 | 棋盘 16 格已清空，只有两个数值为 2 或 4 的初始方块；本局得分为 0；对局状态为“进行中” |
| 基本流程 | 1) 玩家选择“开始新游戏”<br>2) 系统清空棋盘的 16 个格子<br>3) 系统在随机空位生成第一个初始方块，数值取 2 或 4<br>4) 系统在另一个随机空位生成第二个初始方块，数值取 2 或 4<br>5) 系统把本局得分置为 0，对局状态置为“进行中”<br>6) 系统显示棋盘、两个初始方块与得分 0 |
| 例外流程 | 1) 若随机数值不在 2 与 4 之内，系统重新取值，取到 2 或 4 才放置方块<br>2) 若玩家在清空棋盘之前取消操作，系统不改变棋盘与对局状态，用例结束 |
| 被泛化的用例 | 无 |
| 被包含的用例 | 无（UC01 自身被 UC06 包含） |
| 被扩展的用例 | 无 |
| 修改历史 | 建立于本实验；名称与功能 F01 统一 |

#### 4.5.2 UC02 移动与合并方块（完整叙述）

| 栏目 | 内容 |
|---|---|
| 用例名称 | 移动与合并方块 |
| 用例标识符 | UC02 |
| 参与者 | 玩家 |
| 用例简述 | 玩家按上/下/左/右方向键，系统将全部方块向该方向滑动，相邻同值方块合并为一个双倍数值方块，同一方块每步只合并一次 |
| 前置条件 | 对局状态为“进行中”，棋盘上至少有一个方块 |
| 后置条件 | 方块已完成滑动与合并；若为有效移动，随机空位已生成一个 2 或 4，得分已累加；状态可能因 UC04 变为“胜利”或因 UC05 变为“失败” |
| 基本流程 | 1) 玩家按下上/下/左/右方向键<br>2) 系统把全部方块向该方向滑动到最远的空位<br>3) 系统把相邻且数值相同的两个方块合并为一个双倍数值方块，每个方块每次移动最多只合并一次<br>4) 系统按合并所得数值累加得分并显示（包含 UC03）<br>5) 系统在随机空位生成一个数值为 2 或 4 的新方块<br>6) 系统判断是否出现数值 2048 的方块，满足时执行 UC04<br>7) 系统判断棋盘是否已满且任意方向都无法移动，满足时执行 UC05<br>8) 系统刷新棋盘显示，等待下一次按键 |
| 例外流程 | 1) 若方块无法滑动且没有可合并的方块，本次为无效移动：不合并、不计分、不生成新方块<br>2) 若有效移动后棋盘已无空位，跳过生成新方块，直接进入步骤 6) 与 7) 的判定<br>3) 若判定胜利，置状态“胜利”并提示，不再执行步骤 7)，不再接受方向键输入<br>4) 若判定失败，置状态“失败”并提示，不再接受方向键输入 |
| 被泛化的用例 | 无 |
| 被包含的用例 | UC03 计分与显示得分、UC05 判定游戏结束 |
| 被扩展的用例 | UC04 判定胜利（扩展点“棋盘出现数值 2048 的方块”） |
| 修改历史 | 建立于本实验；计分初稿写在 UC02 内部，改为包含 UC03 后重写步骤 4) |

| 用例 | 前置条件 | 后置条件 | 基本流程要点 | 例外分支要点 | 关系 |
|---|---|---|---|---|---|
| UC03 计分与显示得分 | UC02 的有效移动已完成合并 | 得分已累加；超过最高分时最高分已更新；显示已刷新 | 1) 取本次合并数值之和；2) 累加到本局得分；3) 与最高分记录比较；4) 高于最高分则更新最高分；5) 显示得分与最高分 | 无合并时累加值为 0，得分与最高分不变；最高分记录为空时以 0 为初值 | 被 UC02 包含 |

## 五、实验数据分析与讨论

本实验先在纸上确定参与者与用例，再在 StarUML 7 中落图，绘图过程中共做了四处修改，逐条记录如下。

第一处修改是关于参与者的数量。初稿为了让“判定胜利”“判定游戏结束”有用例可挂，画了两个参与者：玩家与系统。检查指导书对参与者的定义后确认，参与者必须位于系统之外，而系统自身的判定与计分行为发生在边界之内，把系统画成参与者等于承认“系统和系统自己交互”，与实验要求矛盾。修改后删去“系统”这个参与者，UC03、UC04、UC05 不画参与者连线，操作者在用例叙述里记为“系统（由 UC02 触发）”，用例图只保留玩家一个参与者。

第二处修改是关系类型的选择。初稿把 UC04 判定胜利画成 UC02 的包含用例，理由是“每次移动都要判断有没有到 2048”。对照指导书对包含与扩展的区分后改为扩展：包含是无条件、每次执行都必然发生的行为，而出现 2048 才是 UC04 的触发条件，绝大多数移动都不发生，属于在特定条件下插入基用例的行为，因此应画成 `«extend»` 并由 UC04 指向 UC02，同时把扩展点标注为“棋盘出现数值 2048 的方块”。相应地，UC02 与 UC03、UC02 与 UC05、UC06 与 UC01 三对关系保留为 `«include»`，因为计分与结束判定在每次有效移动后必然发生，重新开始也必然先执行一次开始新游戏。

第三处修改是重复描述的消除。初稿在 UC06 重新开始里把“清空棋盘、生成两个方块、得分归零”又写了一遍，用例图中 UC06 与 UC01 之间只有一条关联线，造成同一个行为有两处定义。修改后把这段行为统一收敛到 UC01，UC06 通过 `«include»` 指向 UC01，UC06 的基本流程精简为 4 步，第三步直接写“执行 UC01 开始新游戏”。用例叙述同步修改，避免两处描述不一致。

第四处修改是泛化关系的取舍。初稿曾设想抽出一个父用例“操作棋盘”，让 UC02 移动与合并方块与 UC06 重新开始泛化自它，以求图中关系“齐全”。但这样做之后，父用例既没有自己的执行者也没有独立的流程，属于为画关系而造用例；同时本系统参与者唯一，用例之间不存在“一般—特殊”的父子语义。最终删除该父用例，图中不出现泛化关系，并在报告中写明“本系统参与者唯一、用例之间不存在父子关系，故未使用泛化关系”。

此外，绘图工具的使用上也做了一次调整。用例图在 StarUML 7 中直接绘制参与者、用例与关系连线后导出 PNG；为保证草稿可复现，`models/drafts/uc-01.mmd` 同时以 Mermaid 记录了同一套元素与关系（参与者用 `((玩家))`、用例用 `([名称])`、系统边界用 `subgraph`），若 StarUML 导出的排版需要重画，可先按草稿还原元素与关系，再在 StarUML 中微调位置，确保两种表达的元素与关系完全一致。
